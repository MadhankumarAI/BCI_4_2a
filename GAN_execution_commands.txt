GAN-Augmented BCI Motor Imagery Pipeline - How To Run
=====================================================
Task: Left vs Right motor imagery, BCI Competition IV Dataset 2a.
Baseline to beat: Code/StackedEnsemble/main.py, 0.72 mean kappa.

Everything new lives in Code/GAN/. Nothing in Code/ was modified, so the
original four pipelines still run exactly as before.

-------------------------------------------------------------------------
1. TRAIN THE GENERATORS  (the long step)
-------------------------------------------------------------------------
    python Code/GAN/train_gan.py

What it does, for each of the 9 subjects:
  - loads only the T (training) session, Left/Right, artefact-free
  - trains 1 "full" generator on all of that subject's training trials
  - trains 3 more generators, one per gate fold, each blind to its own fold
  - samples a pool of synthetic trials from each and caches them

Output goes to Code/GAN/checkpoints/ :
    A0x_synth.npz    synthetic trials + the fold assignment main.py reuses
    A0x_gan.pt       generator weights + training history

Why 4 generators per subject and not 1: step 3 decides how much synthetic
data to use by cross-validating on the training session. If a single
generator trained on all of it produced the synthetic data for every fold,
each fold's "held-out" trials would already be baked into the fakes added to
its training set. The gate would then always vote for more synthetic data.
The per-fold generators are the only thing making that decision honest.

TIMING - READ THIS BEFORE YOU START IT.
    This model is expensive on CPU. Measured on this machine (12 logical
    cores), at the default batch size of 16:

        --preset smoke      seconds/generator   OUTPUT IS NOISE, plumbing only
        --preset fast       ~8 min/generator    27 generators  ~4 hours
        --preset balanced   ~23 min/generator   36 generators  ~14 hours
        --preset thorough   ~50 min/generator   36 generators  ~29 hours

    `balanced` is the default. Always check the real number for YOUR machine
    first - the script times a few actual steps at each resolution and
    extrapolates:

        python Code/GAN/train_gan.py --dry-run

    That prints the per-generator and total estimate and exits without
    training. It also prints the resolved dataset paths.

    Prove the plumbing works end to end in under a minute (the samples are
    deliberately noise at this budget - evaluate_gan.py will correctly report
    them as garbage, and main.py refuses to use a smoke cache at all):

        python Code/GAN/train_gan.py --preset smoke --subjects A01

    Then the real thing. It is resumable per subject, so this is the safe way
    to run it:

        python Code/GAN/train_gan.py --preset fast
        python Code/GAN/train_gan.py --skip-existing        # upgrade later

    Or one subject at a time:
        python Code/GAN/train_gan.py --subjects A01
        python Code/GAN/train_gan.py --subjects A02

    On a GPU machine CUDA is picked up automatically; force it with
        python Code/GAN/train_gan.py --device cuda

WHAT THE TRAINING LOG TELLS YOU
    At every resolution stage the trainer prints a line like

      stage 5 done (len  896): amp x0.88 total / x0.82 in-band,
                               out-of-band 14%, r_v 0.09, aug 0.00

    amp ... in-band   Amplitude of the synthetic relative to real, restricted
                      to the frequencies where the real data has power.
                      Sampled from the EMA weights, i.e. the ones that
                      actually get saved. This should climb towards 1.0 as
                      the stages progress. If it is still far from 1.0 at
                      stage 5, the run is under-trained - raise --preset.
    out-of-band       Share of synthetic power outside the real spectrum's
                      support. Should fall.
    r_v               Memorisation pressure: the fraction of the critic's
                      real-vs-fake score gap that is explained by
                      train-vs-unseen-real. Near 0 early on is correct.
    aug               Augmentation strength, raised automatically once r_v
                      goes above 0.4. Staying at 0.00 early is correct; it
                      should engage once the critic starts to memorise.

    Then, per generator:

      [full] 138 real -> 414 synthetic in 21.0 min
             | lost to CAR 0%, to band-pass 31% | amplitude x0.94 of real

    lost to CAR       Should be ~0%. The generator projects the common mode
                      out by construction; anything else means that
                      projection is not being applied.
    lost to band-pass Share of the raw output the 4-40 Hz filter removes.
                      Falls as training progresses.
    amplitude         *** THE ONE TO WATCH ***  Post-filter amplitude versus
                      real. This is the authoritative figure and the same
                      number evaluate_gan.py reports in its `amp` column.
                      Want ~1.0; outside [0.5, 2.0] you get a warning and the
                      generator is not ready to use.

    Note the in-log "out-of-band" and the "lost to band-pass" figures are not
    directly comparable: the log defines the band as the real spectrum's
    99%-energy support, which includes low-frequency bins that the actual
    Butterworth filter attenuates. The log line is for spotting a TREND; the
    per-generator "amplitude x..." line is the number to judge by.

Useful flags:
    --preset NAME       smoke | fast | balanced | thorough (see above)
    --dry-run           print the time estimate and exit
    --skip-existing     leave subjects that already have a cache alone
    --steps N           generator steps at the BASE resolution. Later stages
                        get proportionally fewer (STAGE_STEP_SCALE in
                        eeg_wgan.py), because at 896 samples one stage costs
                        more than the first three combined.
    --batch-size N      default 16. On CPU cost is near-linear in this.
    --gp-every N        lazy gradient penalty interval (default 4, 1 =
                        textbook WGAN-GP). The penalty needs a double backward
                        and costs about as much as the rest of the critic
                        step; evaluating it a quarter as often at 4x the
                        weight is roughly a 2x speedup.
    --gate-folds N      folds for the selection gate (default 3, minimum 2)
    --no-gate-folds     train only the full generator - faster, but main.py
                        then has no leak-free gate. Do not use for results
                        you intend to report.
    --up-mode nearest   reproduces Hartmann's aliasing comparison. This is an
                        ablation only; it injects high-frequency artefacts
                        straight into the 4-40 Hz band the classifiers read.
    --no-diffaug        turns off the adaptive augmentation. Also an ablation;
                        expect the memorisation check in step 2 to fail.


-------------------------------------------------------------------------
2. AUDIT THE GENERATORS  (fast - do not skip this)
-------------------------------------------------------------------------
    python Code/GAN/evaluate_gan.py

Prints one row per subject. Nothing here feeds into the final model; this is
the evidence that the synthetic data is real EEG and is genuinely new.

    amp        *** CHECK THIS FIRST ***  Per-channel standard deviation of
               synthetic over real, after the same CAR and band-pass the real
               trials get. Want ~1.0. Outside [0.5, 2.0] the script prints a
               warning and you should stop reading the rest of the row - an
               under-trained generator gets the spectral SHAPE roughly right
               long before it gets the SCALE right, and the covariance-based
               models that make up most of this ensemble see the SQUARE of any
               scale error.

    PSD        mean |log10| difference of the power spectra, 1-45 Hz.
               Small is good. A large value driven by excess high-frequency
               power means upsampling aliasing - re-run with --up-mode cubic.

    mu err     relative band-power error, 8-13 Hz
    beta err   relative band-power error, 13-30 Hz
               These two bands are where motor imagery actually lives, so
               these matter more than the overall PSD number.

    FTD        Frechet distance in Riemannian tangent space. Our EEG version
               of FID - tangent space instead of Inception features, because
               tangent space is literally what 3 of the 5 base models eat.
               Lower is better, but see the warning below.

    SWD        sliced Wasserstein distance. Lower is better. Hartmann et al.
               found this tracked realism better than FID did.

    nn         *** THE IMPORTANT ONE ***
               Distance from a fake trial to its nearest real trial, divided
               by the typical distance between two real trials.
                   ~1.0  fakes sit at the same spacing as reals. Target.
                   <0.7  the generator is re-emitting training trials.
                         The run has failed. Do not use that subject's data.
                         This is both a useless-augmentation problem and,
                         clinically, a re-identification hazard.
                   >>1   fakes are off-manifold; undertrained.

    TSTR       train on synthetic, test on real held-out trials
    base       train on real, test on the same real held-out trials
               Want TSTR within a few points of base.

    TRTS       train on real, test on synthetic. Want it near TSTR. Much
               higher means the generator is producing exaggerated, too-easily
               separable class prototypes.

The script prints an explicit WARNING listing any subject whose nn ratio is
below 0.7.

Do NOT pick a generator by best FID/FTD. Hartmann et al. section 5 report
that their best-FID model produced the least realistic spectra, and that the
Inception Score gave no signal at all about a collapsed model. Read the panel
as a panel.

Save it for the record:
    python Code/GAN/evaluate_gan.py --json gan_audit.json


-------------------------------------------------------------------------
3. RUN THE AUGMENTED ENSEMBLE  (the result)
-------------------------------------------------------------------------
    python Code/GAN/main.py

Same 15 base learners as Code/StackedEnsemble/main.py (5 models x 3 time
windows) and the same logistic-regression meta-learner on out-of-fold
predictions. The one change: the base learners may also be trained on
synthetic trials, and whether they are is decided per subject.

Per subject it prints the gate table, e.g.

    gate (3-fold, leak-free):
      gan@1.0          kappa  0.781 +/- 0.031  <- selected
      segrec@1.0       kappa  0.766 +/- 0.028
      none             kappa  0.742 +/- 0.026
      ...
    final base fit: 138 real + 138 synthetic
    >>> gan@1.0          accuracy 88.65%  kappa 0.7730

then the per-subject table and the mean.

The four safeguards, since this is a medical pipeline:

  1. The E (evaluation) session is never used for any decision. The GAN, the
     normalisation statistics, and the augmentation choice all come from the
     T session. E is read once, at the end, for the reported number.

  2. The gate is leak-free - fold k is scored with a generator that never saw
     fold k. Same folds are reused for the meta-learner's out-of-fold stage.

  3. "none" is the default and wins ties. The winner is chosen by the
     one-standard-error rule: a candidate must beat the un-augmented baseline
     by more than one standard error of the fold scores. Taking the plain
     argmax over 6 candidates on ~45 validation trials would itself be
     overfitting. Expect several subjects to come out as "none" - that is the
     safeguard working, not a bug.

  4. The GAN competes against free alternatives in the same pool:
     segment-recombination and Riemannian geodesic re-colouring. If it cannot
     beat methods that cost milliseconds and cannot memorise anything, it is
     not used.

Synthetic trials only ever enter BASE-LEARNER training sets. The meta-learner
is always fitted on out-of-fold predictions for real trials.

Useful flags:
    --subjects A01 A02   run a subset
    --all-candidates     adds the noise/shift controls and a GAN+segrec
                         mixture to the gate. Use for the ablation table.
    --no-gan             ignore the cached generators entirely and let only
                         the classical methods compete. THIS IS THE ABLATION
                         THE GAN HAS TO BEAT - run it and compare.
    --json results.json  save everything, including the gate tables

4. RECOMMENDED SEQUENCE FOR A REPORTABLE RESULT
-------------------------------------------------------------------------
    .\venv\Scripts\activate

    python Code/GAN/train_gan.py --dry-run                  # how long?
    python Code/GAN/train_gan.py --preset smoke --subjects A01   # plumbing
    python Code/GAN/train_gan.py --preset fast              # ~4 h, resumable
    python Code/GAN/evaluate_gan.py --json gan_audit.json   # read the nn col

    python Code/StackedEnsemble/main.py                     # 0.72 reference
    python Code/GAN/main.py --no-gan --json res_classical.json
    python Code/GAN/main.py --all-candidates --json res_gan.json

Three numbers to compare:
    StackedEnsemble          the published 0.72 baseline
    --no-gan                 classical augmentation only
    --all-candidates         GAN in the pool

If the third is not meaningfully above the second, the honest conclusion is
that the GAN did not help on this dataset - which is a legitimate finding at
110 training trials per subject, and is what the gate is designed to detect
rather than paper over.

-------------------------------------------------------------------------
6. TROUBLESHOOTING
-------------------------------------------------------------------------
"cache holds N training trials but the loader produced M"
    A0x_synth.npz was built against different data or a different window.
    Re-run train_gan.py for that subject.

"A0x_synth.npz missing - run train_gan.py first"
    evaluate_gan.py and main.py both need step 1 to have completed for the
    subjects you are asking for.

main.py prints "none" for every subject
    Working as designed if the GAN is weak. Check step 2's amp column FIRST -
    if it is outside [0.5, 2.0] the generators are simply under-trained and
    nothing else in the table means anything. Then check the nn column:
    if it is below 0.7 the generators memorised and need retraining
    (more steps, or leave --no-diffaug off). If nn is healthy and the gate
    still says none, the GAN genuinely is not adding information.

Out of memory / too slow
    Lower --batch-size (default 16) or --steps, or use --preset fast. Memory
    is rarely the constraint; time is. Run --dry-run first, always.

"Dataset paths are not configured correctly"
    Edit PROJECT_ROOT in Code/GAN/paths.py, or set BCI_PROJECT_ROOT /
    BCI_DATA_DIR / BCI_LABELS_DIR. The message lists exactly what is missing.

"the cache was built with --preset smoke"
    Working as intended. A smoke cache is noise; main.py refuses to train on
    it. Retrain that subject with --preset fast or better.

"gate_folds must be at least 2"
    A one-fold gate has no validation set to score candidates on. Use 2+.

aug stays at 0.00 during a long run
    The augmentation controller is driven by r_v: the fraction of the critic's
    real/fake score gap that is explained by train-vs-unseen-real rather than
    by real-vs-fake - i.e. by memorisation. Early on r_v is near 0 because the
    critic has not overfitted yet, so no augmentation is needed and 0.00 is
    correct. If r_v climbs past ~0.4 and aug stays at 0, that is a bug. If r_v
    itself never moves across a whole run, check the W~ column is not stuck -
    the critic may not be learning at all.
